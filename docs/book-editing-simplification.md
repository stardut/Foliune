# 画册编辑围绕当前内容

2026-11-04，配合书架出版物视觉方案，移除编辑器面向用户的版本概念。本记录仅涵盖编辑器、追加选片文案与保存/重排事务；书架视觉见 [出版物书架方案](book-publication-design.md)。

2026-11-06，已有画册的重新排版及撤销入口已移除。当前规则见[产品约定](product.md)。以下为原方案及验收记录。

## 场景与方案

用户进入画册后直接编辑当前内容，主操作为「保存」，成功反馈为「已保存」。顶部保留画册名称、页数和保存状态；不显示手工版、自动版、版本名、历史版本或版本切换入口。播放和 HTML 导出仍在更多操作中，存在未保存修改时禁用。

延续现有中性深色编辑外壳与白色画册纸张，照片和页面预览保持主视觉，删去无助于编辑任务的概念与重复提示。重新排版复用现有模板与纸张比例，不修改照片原件或既有非破坏裁切规则。新增预览对话框复用统一 Modal、按钮、照片页和中性承托面，没有另外引入材质体系。

重新排版遵循以下过程：

1. 在「画册」属性中选模板，点击「预览排版」。后端只校验草稿和生成页面，不写入数据库、不切换当前内容。
2. 在独立预览中逐页检查。明确提示页面文字和照片位置将被重排；取消或关闭预览后继续原来的编辑，未保存修改保持。
3. 点击「应用并保存」才执行事务。若当前草稿与存储内容不同，先在同一事务追加完整源内容，再追加新排版并切换当前内容。任何一步失败，整笔事务回滚。
4. 新排版携带准确的来源 ID，当前内容在此后保存或追加照片时继续保留这条来源。通过「撤销重新排版」确认后可恢复源内容；应用重启和图库备份恢复后仍可使用。

撤销入口在有来源且没有未保存修改时可用。确认说明会恢复重新排版前的页面和文字、之后保存的调整不再作为当前内容；撤销自身也只追加内部快照，不删除任何旧内容。若连续多次重新排版，来源链可以逐次恢复。

## 持久化与并发边界

- 普通保存由更新手工记录改为追加不可变快照。既有 ID、创建时间、类型及 JSON 原文均不更新、不迁移、不删除。
- 保存、应用重排和撤销在事务内核对前端读取的源 ID 是否仍为当前 ID。全部新保存均产生新 ID，因此另一次保存、追加或重新排版会令旧编辑请求被明确拒绝；前端不清空失败草稿。
- 旧 `save_version` 和 `reflow` 调用签名保留；编辑器新增 `books_preview_reflow`、`books_apply_reflow`、`books_undo_reflow` 三个 IPC。
- JSON 仅新增可选 `reflowUndoId`，无数据库迁移。旧记录缺字段时默认无来源，序列化时省略空字段；新保存的来源只能继承当前内容，重排来源由后端确定。
- 来源必须属于同一画册且无循环。画册读取会校验，备份恢复现有的 `books::get` 和布局校验链路同样校验，不静默忽略损坏来源。
- 既往数据没有可靠的来源关系，不能用名称、类型或相邻顺序猜测。本轮不新增历史恢复列表，不为旧记录补写来源；既往全部内容仍随数据库和备份保留。

新增事务与 IPC 位于 `book_editing.rs`；原画册模块保留兼容入口和读取职责。拆分后 `books.rs` 为 452 行，避免把新增编辑事务继续堆入原模块。

## 离开与失败状态

未保存修改继续单独通过 `onDirtyChange` 触发返回书架、跨工作区和原生关窗保护。保存、生成预览、应用和撤销期间通过 `onBusyChange` 独立上报 `bookBusy`；App 在忙碌时阻止导航和关闭，不能通过确认放弃绕过。编辑器操作用即时 ref 防重复请求，并在忙碌时禁用编辑表单和返回入口。

保存或应用失败只显示错误，保留当前草稿、dirty 标记及尚未应用的预览。预览取消不先保存，不产生隐式副作用。选片追加对话框只显示所选照片与目标画册，主操作为「加入画册」，不再说明内部快照。

## 原生灰空阻断与修复

主代理在独立原生实例发现：带未保存修改的画册完成「应用并保存」后，数据库内容正确，但整个 React 界面消失，截图见 `.build/verification/book-publication/editor-applied.png`。这说明静态构建与数据测试不足以替代原生操作，初轮交付未通过这一交互门槛。

按 diagnosing-bugs 建立真实组件回归 `node --test apps/desktop/tests/toast-modal-lifecycle.test.mjs`。测试使用真实 React 19 `createRoot`/`act`、现有 `Modal`、`ToastProvider`、`modal-stack`、真实 portal 与生命周期，并用 happy-dom 提供 DOM。只补充该 DOM 环境未实现的 dialog/popover 平台接口；`showPopover` 在节点断连时严格抛出 `InvalidStateError`，记录每次调用的连接状态。

修复前，应用关闭、撤销关闭和嵌套内层关闭三项均报 `InvalidStateError: Popover is not connected to a document`；普通保存与保持弹窗打开的保存通过。堆栈落在 `ToastProvider` 的 layout effect，证明故障来自宿主生命周期：同批关闭弹窗与成功反馈时，React 先移除 dialog DOM，Modal 的 passive cleanup 尚未通知宿主栈，toast portal 暂时仍在断连 dialog 下。此时调用原生 `showPopover` 会抛异常并使 React 根界面卸载，不是页面数据缺失或数据库保存失败。

修复只在 `ToastProvider` 调用 `showPopover` 前检查 `viewport.isConnected`；现有 Modal cleanup 随后更新宿主，portal 自动迁入 body 或仍打开的外层弹窗，再进入原生 top layer。没有加定时延迟，也没有用 catch 掩盖异常。

补修验证：真实组件回归 4 项全部通过，断言编辑器仍挂载、成功反馈已连接并进入 top layer、嵌套场景迁入正确外层宿主，且从不对断连节点调用 `showPopover`；`pnpm typecheck`、`pnpm build` 和 `git diff --check` 通过。仅新增测试开发依赖 `happy-dom@21.0.4`，不影响应用运行依赖。修复后的原生重建与复验由主代理继续记录，不以模拟 DOM 的通过代替 WKWebView 复验。
